Component Architecture: Web Components & the Layer Cake

How to structure components so they survive framework churn and vary by product without fragmenting.

Web Components as the delivery vehicle

Frost strongly recommends Web Components as a reusable HTML, CSS, and JavaScript delivery format intended to work across different technology stacks and frameworks.1 He presents cross-stack reach as the payoff; this source does not test specific React, Vue, server-rendered, wrapper, event, form, or hydration integrations.

The "layer cake"

Frost's compositional model has two tiers:1

  • Basement / base layer — primitive base components shared by everyone.
  • Recipe layer — more complex, composed components (cards, headers) that may legitimately vary by product.

Separating the two lets the shared core stay stable while product teams assemble product-specific "recipes" on top.

Build on native standards

Frost's guiding principle is to build on native web standards wherever possible to improve longevity as specific frameworks come and go.1 It is a bet that the platform will outlive any given framework, not a guarantee that integration costs disappear.

Keep tokens out of component logic

Frost insists design tokens be kept separate from component logic so they can be themed and updated independently.1 This is the architectural seam that the token architecture page develops in depth.

Components have a data model

Curtis makes the component architecture explicit as data: a component spec can model props, anatomy, default layout, styles, token bindings, variants, slots, and relationships among subcomponents. Instead of enumerating every visual variant, the spec can express defaults plus rules, collapsing redundant Figma structures into code-like intent.4 See Components as Data.

Adaptability needs encoded boundaries

Mall's Part 2 essays add a usability constraint to architecture: components still need to be adaptable, but the boundaries of adaptability should live in the component system rather than in documentation that every consumer must remember under deadline pressure. Layout components that own spacing, token pipelines that validate resolution, and APIs that make invalid usage difficult are architectural choices, not merely documentation choices.3

Perspectives: web-standard reach vs. typed-framework rigor

The current corpus establishes two independently advocated priorities rather than a head-to-head verdict. Frost favors Web Components and native standards for cross-stack longevity.1 McMahon shows how TypeScript discriminated unions and never can reject invalid prop combinations at compile time, with runtime assertions as a second defense.2 Curtis adds that iOS, Android, React, and web require principled mapping across platforms.4

Interim position: choose only after testing the actual platform mix, runtime constraints, and required compile-time guarantees. The current sources do not establish a universal winner or substantiate the integration costs of wrappers, custom events, forms, SSR/hydration, accessibility ownership, or a Web Component core with framework adapters. See Type-Safe Design Systems.
