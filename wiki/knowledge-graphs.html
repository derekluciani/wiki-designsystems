Design Systems as Knowledge Graphs

Deconstructing design systems as non-linear hyperobjects composed of transcluded content, bidirectional links, unresolved fragments, and structured queries.

Beyond the product metaphor

While design systems are commonly treated as standalone software products, libraries, or documentation sites, Chase McCoy argues they represent something far more complex. Good systems are hyperobjects that capture decisions, language, patterns, history, and the collective institutional knowledge of an organization.1 Instead of flat, linear files, a design system resembles a knowledge graph—a collection of interlinked descriptions of entities, concepts, and objects.1

The four graph mechanics

McCoy identifies four core patterns derived from knowledge graph software (such as Roam Research, Obsidian, and Notion) that can be directly applied to design system architecture:1

  • Transclusion: Storing information (styles, tokens, guidelines, properties) in its minimum viable format so it can be referenced and dynamically embedded across multiple contexts.1 Updates to the canonical node can propagate to its embedded instances, reducing drift caused by duplicated copies without reconciling that content against code, Figma, or other sources. Real-world implementations include:
    • Seeds design system: Embeddable, hoverable tags for tokens, components, and properties that show inline details without switching context.1
    • Kiwi Orbit: Inline transclusion tags displaying component metadata directly inside documentation prose.1
  • Bidirectional links: Making components and documents aware of where they are referenced.1 For instance, if a Button component consumes an Icon, the documentation for Button shows it imports Icon, and the documentation for Icon dynamically lists Button as a consumer. This relationship can be visualized as a visual graph or navigated using layered sliding cards (similar to Andy Matuschak's sliding pane interface).1
  • Fragments (Red Links): Creating placeholder entities in the graph that do not yet exist, inspired by Wikipedia's "red links."1 These fragments help new pages enter an existing network, establish a visible backlog of design system needs, and invite community-driven contributions.1
  • Queries: Exposing system content to logical search operators (e.g., query for icons AND onboarding to find onboarding-related assets) and transcluding the results dynamically.1 In his August 2021 essay, McCoy identified Shopify Polaris as a partial example, describing a GraphQL API for design-system content including pages, tokens, components, and examples; the local corpus does not establish that API's later status.1

Graph mechanics are not source reconciliation

Three capabilities are easy to collapse but operationally distinct:

  1. Transclusion reduces duplicate copies. Reusing one addressable node means an edit can appear in every place that embeds it.1
  2. Bidirectional links expose dependency and impact. A component can show what it consumes and which other nodes consume it.1
  3. Reconciliation decides which source wins. When code, Figma, tokens, Storybook, and prose disagree, neither embedding nor backlinks settle the conflict. A separate contract or governance process must compare sources and record precedence; Primitiv's public documentation proposes this layer before MCP retrieval; the corpus does not establish its adoption or effectiveness.3 See Components as Data, MCP & the Machine-Readable Interface, and MCP Case Studies.

Graph structure can therefore reduce one class of documentation drift and make another class visible. It cannot automatically reconcile divergence among implementation, design, token, and documentation sources.

The agentic interpretation: useful affordances, not automatic fixes

McCoy proposed these mechanics in 2021 for human authoring and navigation.1 The table below is the wiki's later interpretation of how they may support agents; it is not a claim that McCoy's source tested agentic workflows.

Graph mechanic Possible agentic contribution Remaining limit
Transclusion Addressable nodes can help an orchestrator assemble a bounded context rather than repeat a full document. Useful context still depends on chunk design, routing, and current canonical content; transclusion alone does not prevent hallucination.
Bidirectional links Explicit incoming and outgoing edges make dependency impact visible to an agent or test runner. Visibility does not run the correct tests or determine whether a linked source is authoritative.
Fragments Named missing nodes can become candidate backlog items that machines as well as people can discover.1 A placeholder does not establish priority, requirements, or permission for an agent to fill it.
Queries Structured retrieval can return bounded system facts; the agentic corpus reports a useful split of JSON for structured MCP payloads and Markdown for natural-language rules.2 A precise query can still retrieve stale or contradictory facts when reconciliation is absent.

Perspectives: linear documents vs. networked graphs

A central tension exists in how design-system knowledge should be structured:

  • Linear, product-centric documentation: familiar pages provide an authored reading path and can be implemented with ordinary documentation tooling. Their boundaries can hide relationships, and repeated content can diverge as the system changes.1
  • Networked, graph-centric documentation: addressable, transcluded nodes expose relationships and permit contextual reuse. They also introduce authoring, discoverability, implementation, and maintenance costs, including custom interfaces such as transclusion hovers or sliding panels.1

Wiki position: a dual interface is a defensible direction, not a resolution of the debate: human-oriented paths can sit over structured, queryable metadata for machine consumers.2 The graph earns its complexity when dependency visibility and contextual reuse outweigh the burden of maintaining nodes, edges, reconciliation rules, and navigational UI. Linear authoring remains viable where those benefits do not justify the machinery.
