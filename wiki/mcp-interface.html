MCP & the Machine-Readable Interface

The Model Context Protocol is connective tissue between a design system and an agent—and the structure of what it exposes can materially affect accuracy and token cost.

What MCP does

The Model Context Protocol is a standard for feeding AI tools the real, structured data behind a design — its intent, tokens, variables, and components — rather than letting them guess from screenshots.1 Figma's Dev Mode MCP server turns a Figma file into an interactive context layer that AI coding tools can query: "X-ray vision" for spacing, color, and component logic, enabling higher-fidelity code generation, especially when the system is cleanly structured.1

From interface to infrastructure

Recent public examples show teams packaging MCP as a maintained interface, although maturity varies: Figma documents a broad toolset, Primer React ships an installable package, and Storybook documents preview support for React.61114 See MCP Case Studies & Agent-Ready Infrastructure.

Storybook MCP as connective tissue

In the agentic-2026 session, the Storybook MCP server is demonstrated as the connective tissue that exposes design-system components, APIs, and interaction tests to AI agents in a structured, token-optimized format.2 Storybook's public preview MCP for React operationalizes that idea: agents can query docs, generate or update stories, preview story output, and run Storybook tests, including accessibility checks when configured.14 The system's components, not generic web knowledge, become the agent's vocabulary.

Component specs as MCP payloads

Curtis's components-as-data argument points to what MCP should expose next: not just component names and prose docs, but compact structured specs that describe props, anatomy, defaults, bindings, variants, slots, and constraints. This moves agents from interpreting rendered artifacts to querying component intent as data.5

JSON for MCP, Markdown for LLM

In Indeed's reported benchmark of structured component metadata, JSON matched or exceeded hybrid Markdown+JSON accuracy while using about 80% fewer tokens. The result is specific to that retrieval and evaluation design and does not establish JSON as universally superior.7

The secondary report describes eight configurations and 1,056 input/output prompt events—22 prompts, three runs, two event directions, and eight configurations. Markdown remained useful for natural-language rules and instructions.7 A merged NYSDS PR provides a compatible implementation example rather than an independent benchmark: token lookup returns JSON while theme guidance is served separately as Markdown.10

A bounded heuristic across these cases is structured formats for contracts, concise Markdown for narrative rules; teams should still evaluate format against the local retrieval task. The Indeed case report describes keeping metadata under source control and generating MCP-readable JSON from documentation.7 Atlassian describes a related pattern using modular instruction blocks and a structured offerings.json schema (see Agentic Content & Prototyping Templates).

Expose foundations, not just components

Omitting foundations can leave agents to infer spacing, typography, and color rules, increasing the risk of brand drift.3 Indeed's authors reported foundation drift with component-only retrieval and closer alignment after adding routed foundation and recipe context; the note does not provide an independently reproduced quality benchmark.8 The reported Spotify workstream advances a related architectural hypothesis by separating foundations, component style, and behavior to reduce context burden.13 This is the practical implication of the tokens-as-API idea: the foundation layer should be machine-visible too.

Output shaping is governance

An MCP response is not neutral documentation; it steers model behavior. A merged NYSDS PR defaults token search to recommended semantic tokens, excludes primitive palette ramps, and drops cssValue from discovery responses to discourage primitive-reference misuse.10 The Miro Aura case report says the team added visual descriptions, use cases, categories, and explicit negative constraints when names alone did not provide machine-usable intent.9

Retrieval is not reconciliation

MCP can retrieve design-system data, but it does not automatically decide which source is true when Figma, code, Storybook, docs, and token files disagree. Primitiv's public documentation proposes a reconciliation layer that scans sources, writes a machine-readable contract, and exposes context, conflicts, inferred rules, and violations through MCP; implementation effectiveness and organizational adoption are not established here.12 This suggests a more demanding interface question: not only how agents access documentation, but how they access claims whose provenance and precedence are explicit.

Structured queries and APIs

In an August 2021 essay, McCoy described Shopify Polaris as exposing a GraphQL API for design-system content—pages, design tokens, components, and examples—targeted at documentation sites and Figma plugins rather than directly at end users.4 The source does not establish the API's status after 2021. As a dated precedent, it illustrates a broader query-based pattern: agents can request bounded structured context rather than traverse human-oriented documentation. See Design Systems as Knowledge Graphs.

Perspectives: structured data vs. prose

Several sources favor structured payloads for component and token facts and prose for contextual guidance.37 Figma and Storybook likewise expose structured system context rather than asking agents to infer everything from a rendered picture or a wall of documentation.614 The evidence supports this scoped division, not a universal format rule: schemas are weak at rationale and judgment, while prose is weak at deterministic contracts.
