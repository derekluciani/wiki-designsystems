Components as Data

The next machine-readable frontier after tokens: turning component intent into compact, inspectable, deterministic specs that humans and agents can both use.

The token treatment for components

Nathan Curtis's core claim is that components should be treated as structured data, not merely as Figma visuals, code snippets, or prose documentation.1 The analogy is design tokens: tokens now have stable cross-tool representations, but components still lack a comparable standard for describing props, anatomy, defaults, bindings, variants, slots, and code-only constraints.1

This extends the wiki's token pipeline thesis upward: if tokens are the API for design decisions, component specs are the API for component intent.

Figma as origin of truth, not final truth

Curtis keeps Figma in the workflow because it remains the dominant collaborative canvas for designers, but he rejects it as the ultimate place to keep truth. His formulation: Figma is an origin of truth, while structured specs should become the durable source of truth for a design system.1

The reason is practical. Figma raw data is too large and noisy for either humans or agents to reason over directly: Curtis cites a five-variant alert component with 126 layers and more than 11,000 key-value pairs, and a button whose raw JSON became 42,065 lines before being compressed into a 442-line YAML spec.1 Screenshots and Markdown summaries are also insufficient: they may be compact, but they are not structured enough to express precise design intent or measure exact changes.1

Design intent over inference

The point is not to let AI guess better from design artifacts; it is to remove the need for guessing. Curtis argues for explicit, deterministic rules rather than 80–95% inference from noisy inputs, because production design systems need trust closer to 99.9% correctness.1 The desired component spec is:

  • Human-readable enough for designers to audit.
  • Machine-readable enough for scripts, agents, and pipelines to consume.
  • Complete enough to inspect styles, bindings, props, variants, and differences.
  • Compact enough to avoid drowning agents in irrelevant tool cruft.1

The component spec model

Curtis's proposed YAML model describes components through a small set of recurring structures: props, anatomy, default layout, styles, bindings, and variants.1 Conceptually, it behaves like CSS: define defaults first, then define variant rules as deltas from the default.

The key compression move is to replace variant enumeration with rules. Instead of preserving many redundant disabled button variants, the spec can express one rule such as "if disabled, use the disabled token" or set opacity once.1 Instead of carrying Figma's separate showTitle boolean and title string, a spec can translate that into code-like intent: title exists or it does not.1

Specs as a pipeline, not a handoff

The workflow moves beyond designer-to-developer handoff. Curtis describes tools that fetch Figma data, scan a library, generate YAML specs, and compare raw design data against structured output; those specs then feed code generation, documentation, QA, accessibility audits, visual review, and agent workflows.1 The important constraint is that commands are scripted and deterministic, not merely natural-language prompts, so agents work faster and with fewer ambiguous interpretations.1

Contracts, manifests, and MCP payloads

The selected 2026 notes provide several implementations of components-as-data at different evidence levels. Indeed is reported to have parsed MDX into per-component JSON for MCP/RAG retrieval.2 As publicly documented in July 2026, Storybook's preview React MCP exposes component documentation and stories, while Primer React distributes an MCP package exposing components, examples, patterns, tokens, and usage guidance.34 Primitiv's public documentation describes scanning Figma, code, Storybook, and token files, reconciling conflicts into a contract, and serving that contract through MCP; the corpus contains no independent behavior or adoption evidence.5

The distinction matters: a component spec describes intent; a manifest exposes runtime/documentation facts; a reconciled contract asserts which facts win when sources disagree. Mature agent-facing systems may need all three.

ADRs as schema governance

Structured component data creates governance questions that cannot be left implicit: should geometry use left/right or start/end? Should naming use leading/trailing? How should token references map to component bindings? Curtis recommends architectural decision records (ADRs) that capture context, alternatives, rationale, and the decision, then implement the choice in schema, TypeScript types, and tools.1

This is governance at the schema layer: decisions become durable because they are both recorded and encoded.

Perspectives: structured truth vs. collaborative truth

The live tension is not whether specs are useful; it is whether they accidentally recreate handoff. Curtis notes that after generating specs, teams can stop talking and split back into isolated design and development lanes.1 The healthier pattern uses specs and agents to create gated collaboration moments: planning, spec generation, accessibility audit, visual review, regeneration, and human sign-off.1

Position: components-as-data is not a replacement for collaboration. It is the shared substrate that lets collaboration happen at higher precision, especially when humans and machines are both changing the system.

The maturity horizon: flowing change

Curtis's maturity model is succinct: good design systems ship; better design systems change predictably; the best design systems flow change through an ecosystem in a predictable, performant, error-free way.1 Components-as-data is the mechanism for that horizon: decisions can be seen, diffs can be exact, changes can be traced, and machines can propagate intent without inventing it.
